# SQLite 预计算数据库与缓存加载

数据库已生成并接入精确光线前沿搜索。文件为 `data/search_tables.sqlite3`，大小 **106,000,384 字节（约 101.09 MiB）**，包含 4×4 至 44×44 的 **41 张完整几何表**，以及从原 5,997 题去重得到的 **2,019 张静态前驱表**。它保存光学转移规则，不保存答案、目标命中或动态搜索状态。

## 启动和载入需要多久

在本机 Python 3.12 上测量，每种启动场景使用全新 Python 进程，重复 3 次取中位数。未清空操作系统文件缓存，因此不能把这些数字称为物理磁盘冷读。

| 操作 | 实测时间 |
| --- | ---: |
| 首次整理全部输入并建库，含进程启动 | **29.01 秒** |
| 上述过程中的数据库生成与写入 | **3.58 秒** |
| 首次导入数据库读取依赖 | **9.62 毫秒** |
| 只读打开数据库、检查版本 | **0.52 毫秒** |
| 载入 4×4 的几何＋前驱表，含校验和解码 | **1.00 毫秒** |
| 载入 24×24 的几何＋前驱表，含校验和解码 | **3.48 毫秒** |
| 载入 44×44 的几何＋前驱表，含校验和解码 | **9.16 毫秒** |

正常启动不重建，也不扫描整个数据库。先注册路径，需要某张表时才读取；已经在内存 LRU 中的表直接复用。前驱表仅在搜索需要反向引导时读取，所以部分题只会读取几何表。默认读取、校验和解码时间计入求解超时预算。

另做了一次全库诊断：2,060 张表逐张读取、校验、解码后释放，耗时 **2.77 秒**，枚举键另需约 64 毫秒，进程峰值工作集约 32 MB。这不是全库常驻内存的初始化时间。若全部展开并保留为 Python 对象，按结构保守估计约 **1.40 GiB**；未实际执行该全量常驻操作。默认继续使用两层各 65,536 状态槽的有界 LRU。

全库诊断在移动构建专用依赖之前执行；数据库、读取与解码逻辑未变。最终启动数字来自移动依赖之后的复测，首次依赖导入从 19.78 毫秒降到了 9.62 毫秒。

## 实际求解效果

本轮基线是上一轮已优化的内存缓存版本 `tmp/space_time_release`，候选冻结于 `tmp/database_final`，与生产源相同。每题 1 秒预算，串行隔离持久工作进程；有解结果独立复核完整库存及光路。

| 测试集 | 原内存缓存版 | 数据库版 | 本次耗时降低 | 前后正确完成 |
| --- | ---: | ---: | ---: | ---: |
| 完整 5,997 题 | 51.885 秒 | 50.728 秒 | **2.23%** | 5,997/5,997 |
| 未参与建库的 164 题 | 1.819 秒 | 1.779 秒 | **2.19%** | 164/164 |

均零错误、零超时，没有新增超时。每个配对输入的解、状态和 9 项工作计数完全一致。完整矩阵 P99 从 44.760 毫秒降到 40.161 毫秒，但 P50 从 1.951 毫秒变为 1.978 毫秒，单次最大值从 251.844 毫秒变为 255.685 毫秒；不能声称每题均变快。完整矩阵每版本每题执行一次，约 2% 的总收益属于较小增益。

新进程启动至首个解（含进程启动、模块导入、读题、数据库读取和搜索）的三次中位数如下：

| 代表案例 | 原内存缓存版 | 数据库版 |
| --- | ---: | ---: |
| n04_a04_c04_open | 67.96 ms | 80.53 ms |
| n24_a10_c10_obstacles | 106.51 ms | 117.13 ms |
| n44_a09_c06_obstacles | 175.99 ms | 170.28 ms |

小、中案例的首次求解受固定初始化影响；较大案例才抵消这部分开销。54 次首解/重复求解的结果、布局和全部计数一致，重复求解没有新增数据库读取。首次读取时间与重复查询收益分别保留，没有把预热成本隐去。

5,997 题含 3,998 个有解题与 1,999 个容易的奇偶性无解控制；164 题含 110 个有解题与 54 个无解控制。后者来自上一轮冻结后生成的种子集，未用于构建当前数据库。遇到未收录的静态布局时，仍正常计算对应前驱表。

## 使用

现有搜索命令会自动发现项目根目录的数据库：

```powershell
python -m lazor boards/custom_test.bff --solve --algorithm search
```

指定其他库或临时关闭：

```powershell
python -m lazor boards/custom_test.bff --solve --algorithm search --table-db data/search_tables.sqlite3
python -m lazor boards/custom_test.bff --solve --algorithm search --no-table-db
```

Python 中可配置和查看读取状态：

```python
from lazor.search import configure_search_database, search_database_info, solve_search

configure_search_database("data/search_tables.sqlite3")
result = solve_search(puzzle, timeout=1)
print(search_database_info())
```

`configure_search_database(None)` 关闭数据库；重新配置同一路径会关闭旧连接、清空内存表，适合重载或测量。`clear_search_caches()` 只清除内存表，保留已打开的读取器。环境变量 `LAZOR_TABLE_DB=PATH` 可指定位置，值 `off` 可关闭。默认 SMT 和编辑器的求解策略仍保持原样，本功能用于 `--algorithm search`。

日常运行无需再建库；需要更新时使用：

```powershell
python -m lazor.table_database build data/search_tables.sqlite3 --manifest outputs/scaling_full/manifest.json --predecessors all --overwrite
```

不加 `--overwrite` 会拒绝覆盖已有文件。构建先写同目录临时文件，提交完成后原子发布；失败保留旧库。Windows 上重建前应关闭使用旧库的读取器或进程。其他尺寸、矩形布局可通过 Python 构建接口加入；默认命令生成 4 至 44 的方形尺寸。

## 格式与正确性

SQLite 存储固定宽度、小端 int32 二进制块。每张几何表按尺寸索引，每张前驱表按尺寸和精确的静态域字节索引。SHA-256 绑定版本、类型、尺寸、域及数据；读取时验证元数据、长度、索引范围和校验和，验证完成才放入 LRU。光学规则改变时必须升级 `OPTICS_VERSION` 并重新构建。

缺库、缺记录、不兼容、损坏或 SQLite 被独占锁住时，立即回退到正常计算，读取器不会创建空库。加载过程中保留超时检查；用户进度回调可以读取或清除缓存，重入不死锁，也不会重复计算缓存容量。校验和用于检测损坏与版本混用；数据库应来自本项目构建器，不能把它当作任意外部数据库的真实性认证。

**225 项完整回归测试通过**，包括数据库版本、损坏数据、缓存键隔离、原子发布失败、锁冲突、加载超时、回调重入和命令行选项。数据库哈希已加入基准配置，避免续跑时混用不同文件。最终代码与冻结副本相同，库文件哈希在完成全部测试后仍与建库后记录一致。

结果保存在 `outputs/database_optimization/`：`summary.json`、`comparison.json`、`build.json`、`build_wall.json`、`database_identity.json`、`e2e_final.json`、`e2e.json`、全量和种子 JSONL 及 `regression.txt`。其中 `e2e_final.json` 是最终启动测试，`e2e.json` 保留早期启动结果与全库流式诊断。
