# 按开局结构选择策略与位集预计算

本轮优化对象是精确前沿搜索 `--algorithm search`。策略在验证输入后，读取尺寸、可放格数、库存总数和目标数；不读取案例编号、种子或预埋答案。已有 SQLite 数据库继续使用，无须重新生成。

## 为什么进一步查数据库收益有限

上一轮完整数据中，29～44 边长占总耗时约 67.7%。代表性大盘的乐观可达性检查占 profiler 累计时间约 53%～86%；静态几何数据库消除了部分几何计算，但逐状态执行 Python 循环仍然昂贵。另一些中盘（例如 `n13_a07_c05_obstacles`）主要耗在搜索决策及目标反向距离，不能用同一策略处理。

本轮先在旧案例中选取 147 个开发案例筛选方案，再冻结代码，完整评估 5997 例及生成后的 164 个新种子。开发面板收益不是最终完整测试成绩。

## 完整对比

以下为同机本轮重新测量，基线是已启用数据库的上一版，不与此前不同时间测得的 50.73 秒混算。

| 测试范围 | 旧版算法耗时 | 新版算法耗时 | 下降 | 错误/超时（旧→新） |
| --- | ---: | ---: | ---: | --- |
| 完整 5997 例 | 57.8085 秒 | 36.2246 秒 | 37.34% | 0/0 → 0/0 |
| 冻结后 164 个新种子 | 2.0098 秒 | 1.3599 秒 | 32.34% | 0/0 → 0/0 |
| 完整集内 3998 个有解项 | 57.4730 秒 | 35.8865 秒 | 37.56% | 0/0 → 0/0 |

完整集各尺寸的实测结果：

| 方盘边长 | 题数 | 旧版秒数 | 新版秒数 | 变化 |
| --- | ---: | ---: | ---: | --- |
| 4～8 | 705 | 1.0973 | 1.0791 | 下降 1.66% |
| 9～16 | 1176 | 4.6279 | 4.8828 | 增加 5.51% |
| 17～28 | 1764 | 12.4691 | 11.4750 | 下降 7.97% |
| 29～44 | 2352 | 39.6142 | 18.7877 | 下降 52.57% |

收益集中在原先最费时的大盘。按题型，有障碍题下降 45.52%，开放题下降 28.69%。完整集搜索节点从 3,129,869 减至 2,575,911（约 17.7%），光学状态访问从 108,949,852 减至 85,943,457（约 21.1%）。P99 从 46.24 ms 降至 34.27 ms。

并非每题都变快：单次完整运行中有 36 题增加超过 5 ms；最大单题耗时 286.64→290.90 ms，仍小于 1 秒。原始记录和汇总保留所有退化案例，不只记录收益。较小题目的几何预处理本来就少，批量遍历和维护掩码可能不抵额外成本；少数开放题的位集按层遍历也会比栈遍历先访问更多状态。

最终验证另包括 238 项单元测试，以及 740 次与独立旧版完整枚举/模拟器的交叉审计：346 例默认策略、346 例强制位集及频繁重启、48 例真实稀疏大盘提前引导，全部通过。

为确认局部退化，固定发布代码后，对 147 例开发面板加 12 例退化项交替运行两版，各做 3 次冷/暖缓存测量。面板按每题中位数求和，冷缓存 2.0837→1.3399 秒（下降 35.70%），暖缓存 1.7757→1.0874 秒（下降 38.76%）。但退化确实存在，例如 `n24_a06_c06_obstacles` 暖缓存中位数 16.13→28.16 ms，`n27_a09_c08_open` 为 29.02→44.39 ms。没有用这些复测或新种子结果再调整本次冻结的算法。

## 剩余瓶颈与下一步

1. **赋值/回滚的位集维护**：在 `n24_a06_c06_obstacles` 的 profiler 中，乐观检查累计时间约减半，但 `assign+undo` 从约 4.7 ms 增到 16.5 ms。下一步应实验延迟同步：先记录发生变化的格子，在真正执行乐观检查前合并更新掩码，使两次检查之间反复赋值/撤销的净变化抵消；必须保留库存变化和回滚的精确性。这比继续扩充几何数据库更直接针对当前成本。
2. **少量窄光路的批量开销**：位集按层遍历有时访问更多状态。可实验根据实际前沿宽度切换标量/位集，而不仅按棋盘大小分类；切换收益必须扣除统计、转换和掩码初始化开销。
3. **中盘目标反向距离**：最慢的 `n13_a07_c05_obstacles` 没有启用位集，profile 中 `reverse_distances` 累计约占 42%。可研究缓存相同静态图及目标的距离层，或更紧凑的增量队列；键必须同时绑定静态域和目标，限制容量。此前仅将距离字典换成稠密列表没有明显收益。

这些是基于当前剖析的后续实验方向，并非本次已实现的收益。Profiler 有插桩开销，以上函数时间只用于定位成本，不代替完整计时。

## 开局分类

令 `S=宽×高`、`P=可放格数`、`M=A+B+C 可移动库存`，光学状态数为 `4*floor((2W+1)*(2H+1)/2)`。矩形使用相同面积和状态数规则。

| 条件 | 搜索与缓存策略 |
| --- | --- |
| 不可达的偶数奇偶性目标 | 输入校验后立即返回已证明无解 |
| `S≤64`，方盘 4～8 | 原有逐状态搜索；内存按需几何，省去数据库启动成本 |
| `65≤S<256`，方盘 9～15 | 原有搜索；静态几何和前驱表按需查库 |
| `S≥256`、`M>0`、`P≥4M`、目标不超过 64、状态不超过 20000 | 位集批量计算乐观可达性；缓存尺寸相关掩码；普通搜索所需几何按需计算；前驱表仍按需查库 |
| `S≥900`、`M>0`、`P≥16M`、`P<S` | 额外提前进入目标引导阶段，省去第一轮无目标引导的试探；满足上一行条件时同时采用位集 |
| 密度较高、目标较多或超过状态上限 | 保守逐状态实现；大盘提前引导由上一行独立判断 |

检查间隔仍是 32 个搜索节点。提前引导通过实际的阶段复位进入第二轮，随后恢复原阶段预算；最终完整搜索阶段没有重启截断。无解必须完成穷尽证明；超时仍单独报告。

`lazor.search_policy.analyze_opening(puzzle)` 返回策略对象。搜索结果和文本输出记录策略名称、位集是否启用、批次数、初始化耗时以及尺寸表是否命中内存缓存。

## 更有效的预计算

新增 `lazor/bitboard.py` 按矩形尺寸生成：每个格子的前格/后格状态掩码、4 组直行移位规则和 8 组反射移位规则。使用闭式模板移位构造，不逐个调用状态几何解析；边界掩码阻止穿越棋盘边缘。

搜索赋值或回滚时同步维护透射、反射和未决定格的位集。乐观检查将一批状态交给 Python 大整数的底层位运算处理；反射仍要求后格可透射。库存变化在每次检查入口重新投影到未知格，结果仍是安全的可达性上界。

尺寸表不含目标、光源、动态赋值或解答，可跨题复用。第三个 LRU 最多保留 65536 个状态槽，单张表硬上限为 20000；因单格掩码占用会随状态数增长，该限制不能解释为进程内存上限。编译超时不会发布半张表，清空缓存后正在使用的引用仍有效。

位集盘无需先解码整张 SQLite 几何表，因此跳过这项读取。无需全量启动导入，首次遇到适用尺寸才编译；后续同尺寸命中 LRU。`clear_search_caches()` 也会清掉新缓存，`search_cache_info()` 返回三类缓存统计。

7 次采样的中位数（仅尺寸表，不含每题动态掩码初始化）：

| 尺寸 | 首次编译 | 内存命中 | 单表保留对象 |
| --- | ---: | ---: | ---: |
| 16×16 | 0.076 ms | 0.0027 ms | 约 0.10 MiB |
| 24×24 | 0.245 ms | 0.0034 ms | 约 0.41 MiB |
| 32×32 | 0.890 ms | 0.0041 ms | 约 1.22 MiB |
| 44×44 | 2.858 ms | 0.0077 ms | 约 4.14 MiB |

顺序经过 16～44 尺寸时，该新增 LRU 保留对象峰值约 14.54 MiB，末尾保留 41～44 四张表；这是去重后的 `sys.getsizeof`，不是进程 RSS，也不含活跃搜索额外引用。完整运行中 2842 题使用位集，2813 次命中尺寸缓存；所有题的位集初始化合计 1.272 秒，已计入上述算法总耗时。

## 验证范围与计数解释

完整矩阵为 4～44 的所有方盘大小，A/C 各 4～10 的全部交叉组合，排除超容量组合，包含开放、有障碍、奇偶性无解三类，共 5997 例。每例限时 1 秒；固定旧版与新版源码快照、输入哈希和验证器，同一 SQLite 路径，顺序运行隔离的持久进程。算法耗时包含初始化、搜索、内部完整模拟验证，外部再次检查精确库存与命中情况。

新种子在代码冻结后生成，164 个独立种子覆盖全部 41 个尺寸和 49 个 A/C 对，并排除之前五份清单的输入哈希。它们仍来自同一合成生成器，不能代表所有真实题目。完整矩阵中的 1999 个无解项是容易的奇偶性控制项；另外用旧版完整布局枚举和旧模拟器审计普通不可达情况、位集回滚及提前引导。

位集遍历按层扩展，原实现按栈扩展，因此发现最后目标前的状态数、分支和解答可以不同。`ray_states_processed` 计入批次实际包含的状态，`optimistic_batches` 才是批量循环次数，不能将这两个计数直接相减。提前引导记为一次真实重启，因此新版重启数不适合单独用来判断题目是否更难。

## 未采用的方案

开发实验中，统一降低检查频率虽减少可达性访问，却增加搜索节点并拖慢总时间。加入位集后，大开放盘单独改为周期 128 没有稳定的额外收益，因此保留 32。

预计算逐状态邻接元组增加首次构造开销；缓存成功路径证据需要校验大量依赖，命中只有 3 次；反向距离改成稠密列表也未获得有意义的收益。这些实现均未进入生产代码。原始筛选记录保存在 `outputs/adaptive_experiments/`。

## 复现与原始数据

使用仓库现有的 Python 3.12 环境，工作目录为项目根目录；两版均显式指向同一个现有数据库：

```powershell
$env:LAZOR_TABLE_DB = (Resolve-Path data/search_tables.sqlite3).Path
python -m lazor.full_benchmark --manifest outputs/scaling_full/manifest.json --root tmp/adaptive_baseline --output outputs/adaptive_optimization/reproduce_baseline.jsonl --method search --timeout 1
python -m lazor.full_benchmark --manifest outputs/scaling_full/manifest.json --root tmp/adaptive_release --output outputs/adaptive_optimization/reproduce_release.jsonl --method search --timeout 1
```

冻结代码位于 `tmp/adaptive_baseline/lazor` 和 `tmp/adaptive_release/lazor`。结果目录 `outputs/adaptive_optimization/` 中：

- `baseline_search_1s.jsonl`、`release_search_1s.jsonl`：完整集逐例结果、源码/输入哈希。
- `fresh_baseline_search_1s.jsonl`、`fresh_release_search_1s.jsonl`：新种子逐例结果。
- `fresh_holdout/manifest.json`：新种子、排除范围及生成前冻结哈希。
- `comparison.json`：全部分组、状态转换和退化案例。
- `verification_summary.json`、`unittest_final.log`：单元测试和独立审计。
- `cache_memory.json`：初始化耗时样本及逐尺寸保留内存。
- `recheck.json`：159 例的交替冷/暖三次复测。
- `profiles/regression_profile.json`：剩余慢例的函数级剖析。
